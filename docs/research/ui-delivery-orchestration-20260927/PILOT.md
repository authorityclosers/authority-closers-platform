# Pilot to choose the lightest workflow that meets the visual bar

Proposed, not run. No claimed speed, cost or fidelity winner.

First calibrate one report overview screen family from the selected Drive direction. Use a single implementation owner and an independent review; settle shared tokens and what the comparison means before evaluating throughput. The reference manifest records original bytes and intended provenance. Resolve any reference correction without generating a new visual direction.

Then compare two delivery methods on matched existing screen families:

- A: one capable implementation agent plus the same independent final acceptance reviewer.
- B: the same implementation model/effort plus one Luna helper for bounded inventory/test triage; same acceptance reviewer.

This tests the helper's contribution without confounding it with a change in coding model. A subsequent small comparison can change the implementation owner between Opus and Sol while keeping the other conditions stable. After that, vary effort within the selected model with the same screen class, reviewer and verification requirements. Do not claim a model or effort comparison from A versus B alone, and do not pay for all comparisons unless the decision still needs them.

Prefer two matched pairs from the existing Calls and report-evidence states, matched by components, actions, state count and starting code. Randomize or alternate A/B assignment within pairs and vary run order. Workers start fresh with identical shared component revision, packet size and supplied tests. Do not give later workers earlier solutions. Keep one implementation at a time on this PC. A few cases are diagnostic, not a statistically established universal ranking.

Each method must satisfy the same gate: reference fidelity, responsive reflow, required interactions, keyboard/reduced-motion/content stress, no unresolved critical/high defects, and an independently adjudicated receipt. Keep reviewer feedback scope and maximum correction/escalation policy identical. Mask model identity from screenshot reviewers where practical.

Record:

| Metric | Definition |
|---|---|
| Accepted families | Denominator for time/usage; unfinished families remain failures |
| Active completion time | Start of implementation to acceptance, including repairs and coordination |
| Quota/queue wait | Separate from active work; never conceal it |
| Model usage | Coordinator + writer + helper + review + failed attempts, observed where exposed |
| Cash charge | Actual billed amount separately from subscription usage or estimates |
| Repair rounds | Number and cause, including repeated same mismatch |
| Escaped defects | Found during independent review or staging after worker's claim of completion |
| Reference drift | Explicit deviations in layout/type/density/navigation, adjudicated by evidence |
| Human effort | Minutes needed to clarify, review or rescue work |
| Coordination faults | Colliding files, duplicate runs, lost context or stale output |
| Machine pressure | Peak observed resources and interference with responsiveness |

Stop the run at its predeclared time/usage cap; record unfinished, do not lower the quality bar. Pause for health-check exit2, auth/billing ambiguity or conflicting file ownership. After two repeated unsuccessful repairs, diagnose the packet/model/tool cause and record any escalation usage separately. The caps must be filled from available quota before execution, not invented by this research.

Choose the simpler method when both satisfy the bar and differences are inconclusive. Keep the helper only if it reduces accepted-family effort or catches meaningful defects for tolerable usage. Adopt Paperclip only in a separate coordination pilot if lost tasks/cross-host recovery are observed, not because this tiny experiment proves all swarms useful.

No paid API experiment, additional subscription purchase or production run is authorized by this document.
