# AUT-988 organisation call read policy

Source: owner-approved AUT-988 card, based on the AUT-741 role matrix. Base:
`a9b8fad8612897bc4729e3191dbc2ba97df11d26`; lane `api`, branch
`task/api/988-org-call-policy`. `ac-gate start api 988-org-call-policy` claimed
the free lane, and `ac-gate check` passed.

The saved-call library and summary now reuse `_account_library_query` with
`every_owner=True` for a current active owner/admin of a registered organisation.
Call detail, report JSON and their labels explicitly opt into the same policy.
Admission checks the selected session, verified active person, active tenant and
current membership. The role query refreshes the identity map and takes shared
transaction locks; demotion/removal applies on the next request. Exact reads of
another person's call also use the library's immutable binding, account claim,
canary exclusion and retention scope.

The default of `require_submission_owner`, `AcquisitionReports.recording`,
`report` and `progress` remains owner-only. Write, source/audio, transcript,
waveform, export, processing-continuation and sharing callers receive no broader
authority. Processing ownership and usage receipts are not reassigned. Personal
has no organisation registry marker; operations is excluded both by HTTP workspace
admission and by the organisation role helper.

Additional allowed production file: `submission_labels.py`, to let read-only
labels accompany an authorised organisation list/detail/report while keeping its
write gate strict. The shared `seed_call` test fixture accepts a visitor id so
legacy claimed/unclaimed receipts can be inserted without rewriting history.

The existing web parser in
`apps/sales-xray-web/app/acquisition-client.ts::parseSubmissionLibraryPage` rejects
extra fields on both the page and each row. Existing requests keep their exact
JSON shape. A future screen client can opt into rep metadata with
`GET /v1/conversation/acquisition/submissions?include_owners=true`, optionally
with `&before=<submission UUID>`. The flag affects metadata only; the server
chooses the visibility scope from current membership. Member/Personal responses
retain the existing row shape even when the flag is supplied. Duplicate and
unrecognised query keys remain rejected. No web files changed.

Final JSON shapes:

- List: `{submissions: SavedCall[], next_cursor: UUID | null}`.
- SavedCall: `{submission_id: UUID, created_at: ISO8601, duration_seconds: int,
  display_name: string | null, display_name_revision: int, state: string,
  has_report: bool}`. Opted-in organisation owner/admin rows also contain
  `{owner_person_id: UUID, owner_name: string}`. Names use the same display-name
  or masked-email fallback as organisation activity.
- Summary: `{total: int, completed: int, processing: int, needs_attention: int}`.
- Detail: the existing progress JSON plus `display_name` and
  `display_name_revision`; no new fields.
- Report: the existing `ac.sales-xray.report-envelope/2` with account access,
  plus the existing label fields; no new fields or scoring changes.

## CTO review changes, 4 Oct 2026

The CTO approved the security design at `5fb902da17a737d857680d3074dc7cebd4b7bb93`
and requested corrections for two CI regressions. No production behaviour or
security design changes are needed in this delta.

The summary regression was reproduced locally on the original head: seven
read-only statements ran, but the old test expected five admission statements
plus one count. The contract is account admission + one current-role authority
check + one count statement. The corrected PostgreSQL test also asserts that the
additional statement reads the caller's membership in the selected organisation,
joins the organisation registry and takes `FOR SHARE`; the final statement is the
aggregate count. The current role remains checked on every request.

The original browser CI JUnit artifact for run `37184877043` reports
`plan_state='completed'` and three `succeeded` inference jobs. Its log's sanitized
failure summary truncates the plan state; the empty text is not evidence that a
plan was absent. The browser's `recovered_report` test adapter did not accept the
new explicit `allow_organisation_read` argument supplied by the HTTP report
route. Invoking that exact adapter locally with the HTTP keyword reproduced
`TypeError: recovered_report() got an unexpected keyword argument
'allow_organisation_read'`. The synthetic processing pipeline completed while
report GETs failed before reaching the real report service. This is a test
adapter regression, not a flake. The repair explicitly forwards the flag to the original report method without
granting any additional authority.

Additional allowed test files: `tests/database/test_conversation_submission_summary_postgresql.py`
updates the constant-query contract for the required current-role read;
`tests/e2e/test_sales_xray_acquisition_browser.py` updates the synthetic retained-C5
adapter to match and forward the real report service's read-policy keyword.
