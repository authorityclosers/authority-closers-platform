# Admin learner minute-account UI evidence

This UI slice is based on the isolated application source at `f4d7bfe97e1a1f7d1151d7cb744e0b2155b84c0b` and the reviewed account-ledger evidence in `20260925_ACCOUNT_MINUTE_GRANTS.md`. The grant route contract comes from the canonical minute-account implementation. The target resolver is pinned to `ba43e5ac620f81e905e9131b11ae9e6c1447ce41`; its strict request contains only `{ "query": string }`, and the server supplies a fixed audit reason so search terms do not enter the audit reason.

The Sales Xray settings route now mounts an Admin panel that performs one exact email or public-username lookup, then reads the server-authoritative account balance for the returned tenant/person pair. The client rejects UUID-shaped and phone-shaped queries locally, sends no query parameters, ignores stale or aborted lookup results, verifies the account IDs match the resolved identity, and renders the shared upload allowance separately from the account-minute ledger. `stored_unlimited` and `effective_unlimited` are shown as read-only status; the UI has no unlimited control.

The grant form accepts a positive whole-minute count within the server's JSON-safe integer limit and a trimmed 1–500 character reason. It creates one secure idempotency key and submits through the canonical same-origin API. The fetch pattern matches the existing Sales Xray Admin request wrappers (`credentials: same-origin`, `cache: no-store`, `redirect: error`); the grant endpoint checks the authenticated platform-access capability and safe request origin. There is no separate shared `adminFetch` wrapper in this source revision.

Before sending a grant, the UI writes a strict, versioned pending-intent record to this browser tab's `sessionStorage`. The record contains actor tenant/person IDs, target tenant/person IDs, exact minutes, audit reason, and idempotency key; it omits the lookup query, email, display name, and masked email, and it is not sent to telemetry. The UI warns before document unload while an intent is unresolved. After navigation or reload, the user must resolve the learner again; the client restores the exact payload only for the same resolved Admin tenant/person identity. A different actor sees a generic unresolved marker and cannot create a new grant for that target. Storage read/write errors fail closed before a grant is sent. No automatic retry occurs.

A grant is reported as confirmed only after a strict response is parsed and its amount and account identity match the submitted intent. Network, conflict, server, or malformed-response uncertainty keeps the amount, reason, and key locked for an explicit same-request retry. Once any attempt is uncertain, later authorization or validation errors keep the marker and same key; they cannot be cleared into a new grant. A replay response confirms the original grant without claiming a duplicate. A definitive rejection clears the marker on the original known attempt. If storage prevents clearing after a confirmed response or definitive rejection, the panel stays locked and offers a local-only recheck. It removes only an absent or exact actor/target/key/amount/reason record; storage failures or mismatches remain blocked, and the recheck does not call the grant API or create a new key. Permission, input, and 422 lookup rejections use safe fixed messages. No provider or analysis request is involved.

- Focused component suite: 15 tests passed with one Vitest worker. Added coverage verifies server-side 422 lookup guidance and local recheck behavior after storage clear failures for both confirmed and definitively rejected grants; recheck issues no second API call and keeps the grant action blocked until the exact marker is safely reconciled.

- ESLint passed on `minute-account-admin.tsx` and its test with `--max-warnings 0`; Prettier check passed on both files.
- The focused checks used the local pnpm cache; all 407 packages were reused without downloads. No provider request, staging/production operation, or browser claim was made.
- Recovery is tab-scoped: `sessionStorage` survives reloads and same-tab navigation but is not a shared cross-tab ledger and is cleared when the tab is closed. The component warns while a known pending grant is mounted; this does not provide cross-tab or after-close recovery. Cross-tab recovery would require a separately reviewed storage/ledger contract.
- Browser rendering, keyboard walkthrough, and responsive visual inspection remain unverified. These results are offline unit/component checks, not activation or release evidence.
