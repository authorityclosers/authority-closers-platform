# Account minute grant implementation evidence

This change adds an operations-host read and grant API for the existing Sales Xray `ConversationMinuteAccount` ledger. It is based on source `234ca575fada1c21f1e6a11fd347caa0d623e0e0`; it introduces no database migration and does not alter the provider-spend budget ledger.

`GET /v1/admin/conversation-minute-accounts/{tenant_id}/{person_id}` returns the exact minute-ledger balance in seconds, whole available minutes, revision, and immutable grant history. It separately reports `shared_upload_allowance_seconds`, `shared_upload_committed_seconds`, and `shared_upload_available_seconds`, which match learner upload admission. The response labels the stored snapshot flag `stored_unlimited` and reports `effective_unlimited` only when the current pinned account-minute tester scope allows it; an old stored flag alone does not grant access. `POST /v1/admin/conversation-minute-accounts/{tenant_id}/{person_id}/grants` appends a positive whole-minute grant with a bounded reason and required `Idempotency-Key`.

Both routes require a current persisted platform-scoped `platform_access_manage` capability through `platform_projection`. This capability is independent of tenant roles; the route does not infer authority from email, owner/admin role, or caller-supplied permission flags. The target must be an active, verified person with an active learner membership in the exact requested active learner tenant. A target in the configured operations tenant, another tenant's membership, and support/admin memberships are rejected. Capability revocation and expired sessions deny later reads and grants.

Each successful grant and its account snapshot update share the authenticated transaction. The operations-tenant audit event records actor/session, exact target tenant/person, minutes and seconds, reason, request digest, and idempotency key. Replays return the original grant ID without adding another grant or audit event; reuse of a key for different request content conflicts. The learner upload and C1 admission cap is 3,600 seconds plus only grants whose snapshot entry matches the exact canonical operations audit event and payload. Hosted initial allowance grants and tester flags remain separate; committed acquisition, claimed-visitor, and account usage is subtracted once. The PostgreSQL regression proves a claimed 3,500-second visitor reservation, 5,980 seconds of account acquisition, and a 120-second C1 reservation reach exactly 9,600 seconds under a 100-minute audited addition; a subsequent C1 request is denied without changing that balance. Balance reads annotate grants created by this route with their audit timestamp and sequence. The existing provider-spend budget ledger is untouched.

Minute amounts use the exact JSON-number integer range commonly supported by browser clients, with the one-hour base allowance kept in range. The endpoint rejects an individual request outside that range and rolls back a grant whose cumulative seconds would exceed it; it does not impose a product-level minutes cap.

Granting takes the target Person lock with `NOWAIT`, then rechecks the active tenant and learner membership under compatible locks before changing the account. A concurrent account update returns a retryable `409 conversation_minute_target_busy`; the transaction rolls back and the caller retries with the same idempotency key. This avoids a mutual-admin lock cycle while allowing an operations manager to also hold learner membership.

A follow-up concurrency review found that target locks alone do not serialize one actor reusing an idempotency key against two different learners. The grant route now acquires the existing PostgreSQL operations-tenant idempotency lock before marker lookup, matching the established retry and reconciliation routes. A fresh PostgreSQL regression concurrently grants the same actor/key to two learner targets and verifies exactly one success, one idempotency conflict, one audit event, and one matching ledger grant; the pair completes within the test timeout.

Verification on the disposable schema-isolated PostgreSQL test database: 8 tests across `tests/integration/test_c1_audited_minute_allowance_postgresql.py` and `tests/integration/test_operations_http_postgresql.py` passed in 85.75 seconds. The grant journey covers persistence, audit-chain validity, no duplicate replay, changed-payload conflict, same-request and distinct concurrent grants, two different managers granting the same learner, held-target `NOWAIT` conflict, mutual manager/learner contention with same-key retry, the 3,600-second base plus a 6,000-second audited grant and upload reservation, exact-cap C1 admission, parity between learner admission and admin shared-upload projection, untrusted hosted/dangling/reused grant markers, stale stored tester flag versus effective policy, JSON-safe integer bounds and rollback, ordinary tenant-admin denial, non-learner, inactive-person, inactive-membership, missing-membership, and foreign-membership rejection, expired-session and revoked-capability denial, and unchanged provider-budget snapshot/revision. Ruff lint/format checks passed for all 9 touched Python source/test files; Mypy reported no issues in all 313 `ac_platform` source files.

After the cross-target idempotency fix, `pytest -q tests/integration/test_operations_http_postgresql.py -k account_minute_grants` passed (1 passed, 2 deselected, 15.50 seconds). Ruff formatting and lint checks passed for the two Python files changed by this follow-up.

No production, staging, provider, notification, SQL-recovery, or UI action was performed. User access-request and notification flows remain outside this backend grant/read slice.
