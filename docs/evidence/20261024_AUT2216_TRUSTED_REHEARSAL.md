## Correction 1: installed trust and candidate containment

`infra/release/trusted_rehearsal/harness.py` must be installed separately from any candidate checkout. Root selects the reviewed bundle in a fixed root-owned configuration, never a candidate argument. The launcher uses an independently installed Python with `-IB`: no current-directory imports, user site, environment Python customization or bytecode writes. Fixed configuration and every parent must be root-owned, without symlinks or group/other write access. The installed script must resolve to the configured bundle. The exact manifest file set and aggregate SHA-256 pin include the harness, exporter, its backup transport, gate, classifier and host requirements lock. An extra file that can shadow imports is rejected. A changed exporter or validator fails before export. The bundle cannot be the workbench or candidate tree.

Only the installed exporter obtains staging credentials, through its existing backup transport. Its subprocess gets a fixed minimal environment, not the caller's credentials. The installed gate parses candidate migrations as data; it does not import their modules. Host Python imports only the trusted installed gate/classifier and the separately installed locked psycopg runtime. Candidate code never installs into that host Python.

Candidate commits are materialized as data from full SHA Git archives in a private run directory. Traversal, absolute paths, symlinks, hardlinks and nonregular objects are rejected; extracted source is bounded at 128 MiB. The candidate/base ancestor relation is checked. No candidate checkout hooks, fsmonitor, filters or executable dependencies run on the host.

The gate's migration executor is replaced with a container adapter. Both dependency installation (`uv sync --frozen --offline --no-python-downloads`) and every Alembic invocation run with UID/GID 65534, network none, read-only root, all capabilities dropped, no-new-privileges, private PID namespace, IPC none and CPU/memory/process limits. The two host mounts are the immutable candidate snapshot and the run's disposable PostgreSQL Unix socket directory, both read-only. No Docker socket, service environment, host home, config, receipt, key, trusted bundle or release directory is mounted. Writable workspace/cache exists only in bounded tmpfs. Container names are generated by the trusted process. Timeout/failure removes that exact container and anonymous volumes in finally; source and schema evidence are deleted with the private run directory. Cleanup failures prevent PASS.

The trusted controller alone uses the host Docker socket. Disposable PostgreSQL uses the existing digest-pinned PostgreSQL image, network none and no TCP publication/listener. Candidate code has only its fictional database credential and its Unix socket. SQL functions or COPY PROGRAM in that disposable server cannot reach the host Docker socket or service configuration. This is a container process/filesystem/network boundary, not environment filtering alone. It assumes the reviewed container engine/kernel security boundary; runtime escape resistance is not proven by unit tests.

The runner image must be separately reviewed, digest-pinned, locally present and secret-free. It must supply Python 3.12, uv at `/usr/local/bin/uv`, `/bin/sh`, cp, and a read-only preseeded `/opt/uv-cache` sufficient for the candidate's frozen lock. No package download or image pull is permitted during rehearsal. A changed lock requiring uncached dependencies fails closed and needs a newly reviewed image. No image was built or selected in this source-only run; no invented image digest is supplied. The config rejects mutable image tags. The host runtime lock selects cp312 Linux x86_64 binary wheels only; it is independent of candidate dependencies.

## Candidate/base receipt contract

The HMAC-SHA256 envelope has exactly `record` and `hmac_sha256`; the MAC covers sorted compact UTF-8 JSON of the complete record. A separately installed 32-byte root-only key authenticates producer and consumer. The CLI never accepts key, receipt directory, exporter, validator, bundle, config or image overrides. Test keys are fictional; no real key was created or read.

The record has exactly: schema `ac.schema_rehearsal/2`, candidate/base full 40-character commit SHAs, bundle_sha256, runner_image digest, result PASS, exported_at, finished_at, manifest_sha256, dump_sha256, alembic_revision and staging release_id. Candidate and base are compared for exact equality, not ancestry equivalence or migration-tree equivalence. The producer checks base ancestry and derives the exact base head from its snapshot. Manifest/dump and source pins cannot be taken from candidate text. Only successful trusted rehearsal creates a receipt.

Receipts are appended with candidate/base plus UTC microsecond timestamp and nonce, using O_EXCL, restrictive mode and fsync. Prior audit evidence is never overwritten. Verification reads only the latest record in the fixed protected candidate/base namespace; it rejects missing, malformed, wrong-MAC, failed, mismatched candidate/base, wrong bundle/image, invalid identity/digests, future-dated or stale evidence. A receipt expires one hour after completion, and evidence expires 24 hours after export. The exact PR head/base is checked again before merge. Changing trusted code/image/key invalidates old evidence. No receipt is a production deployment claim or permission.
