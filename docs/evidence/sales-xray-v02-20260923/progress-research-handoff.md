## Decision

Show confirmed work and useful choices: a stable explanation, recording/transcript/evidence/report trail, saved-work receipts, one optional disclosure, and explicit recovery. Separate server processing facts from client refresh failures and local foreground observation time. Remove automatic cue rotation and continuous decorative rings from analysis. Use short state-change transitions with reduced-motion support.

An unchanged minute of foreground observation may disclose that no new stage has been observed. It does not measure remaining work or infer provider failure. Queued work is not described as running. A completed C4 row without C5 means some work is saved, not that every chunk is complete. `has_report` still requires validated transcript/report retrieval before report display. Unknown statuses retain a conservative checking presentation.

Status observation must perform GETs only. The former polling effect also requested and accepted plans. Keep authorized fresh-upload continuation separate; recovered calls and manual status refresh cannot recreate upload consent or implicitly authorize more processing. Leaving is described as safe for background processing only after accepted automatic progression is confirmed. Being signed in does not establish ownership of an unclaimed guest call.

## Evidence and limits

- [Harrison, Yeo and Hudson, CHI 2010](https://chrisharrison.net/projects/progressbars2/ProgressBarsHarrison.pdf): primary paper inspected locally. Visual manipulations affected perceived duration in short laboratory comparisons. Its final experiment used five- and fifteen-second waits and explicitly required further work to establish longer-duration transfer. This does not justify fake progress or predict trust during an hour-call job.
- [Conrad et al., Interacting with Computers 2010](https://www.rti.org/publication/impact-progress-indicators-task-completion): author-institution abstract verified locally. Slow early feedback harmed questionnaire completion; favorable feedback did not necessarily improve completion. Transfer to background analysis is uncertain. More animation or more progress information is not automatically better.
- [Hui and Zhou, 1996](https://onlinelibrary.wiley.com/doi/abs/10.1111/j.1559-1816.1996.tb00093.x): cloud research distinguishes perceived control from perceived duration. The product inference is to clarify safe actions and recovery, not promise a shorter subjective wait.
- [Buell and Norton, 2011](https://pubsonline.informs.org/doi/10.1287/mnsc.1110.1376): operational transparency can change perceived value. Our constraint is to explain actual saved work, without manufactured effort or artificial delay. Perceived value is not evidence of report accuracy.
- [W3C status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html): verified locally. Announce meaningful status changes without moving focus; avoid an excessively chatty live region. The interactive card and controls are outside the narrow announcer.

Game theory adds no demonstrated first-release mechanism here. The useful constraint is that categorical claims must hold across the server histories compatible with observed facts. No ETA ships: the API lacks chunk totals, event times, revision ordering, queue position, or provider heartbeats. A future ETA needs real duration cohorts, censored unfinished work, failure/held outcomes, calibrated uncertainty, and drift checks.

## Artifacts and verification boundary

The cloud packet reports 56 Node conformance cases, 16 traces/89 events/60 assertions, and four caught injected faults. It explicitly did not run Vitest, repository integration tests, browsers, or production. These are **cloud claims**, not local application evidence. Cloud ZIP delivery has encountered Chrome attachment blocking in this research batch; no block was bypassed and the proposed toolkit is not represented as downloaded or locally executed.

The [design chat](https://chatgpt.com/c/6ab370c0-f420-83e8-b04b-f90cef176297) generated actual desktop and mobile processing reference images. Images are private design artifacts, not implemented screens or device-fit evidence. Unsupported decorative search/navigation/identity details in generated references are excluded from implementation. The local implementation uses native semantic components and real stage data.

Local acceptance must cover: read-only refresh after failed approval; guest restoration without new writes; queued/running distinctions; partial C4; two-hour silent waits; foreground/hidden timing; offline/reconnect; aborted old-call responses; report-validation failures; 320/390/1440-pixel layouts; keyboard/reduced motion; long mixed-script content. Readiness and recovery may not wait for animation. Browser and production results belong in the implementation evidence, not inferred from these research outputs.

## Falsification and fallback

The cloud recommendation proposes a counterbalanced twelve-person diagnostic with identical backend event traces. Compare status comprehension, mistaken retry/re-upload, recovery action/time, missed readiness, and informed return-later versus actual abandonment. No participants have been recruited and no conversion claim is made. Simplify or reject the design if users confuse saved partial work with completion, miss readiness, or leave before approval believing it is accepted.

Confidence is high in the observation/write boundary and factual-state constraints, provisional in UX benefit until usability checks. Bounded fallback: retain the previous verified runtime while the candidate is tested; do not broaden retries, data access, or provider spending. Stop release on source-identity, ownership, approval, or report-validation regressions. Keep only the affected capability gated.
