# Sales Xray review API contract

> Superseded access mode (2026-09-13): the user requires reviewer-only login and
> workspace access, separate from learners. The Academy form/session statements
> below record the prior implementation and no longer authorize release. See
> `REVIEWER_ACCESS_SEPARATION.md`. The legacy learner reviewer routes are held;
> source binding and append-only feedback contracts remain applicable.

## Current interim transport boundary

The generic learner review routes listed in the historical contract below are
not installed and return 404. Admin assignment/invitation creation retains its
authorization checks and returns 503 without creating an assignment, invitation
or email outbox event. Existing Admin list and revoke routes remain installed.

`GET /v1/admin/conversation/review-assignments/{assignment_id}` is a separate
private, no-store Admin detail read. It accepts no scope query parameters and
requires the canonical AC operations Admin authority. It returns `assignment`,
`lifecycle`, source retention metadata, review/report/checkpoint metadata,
`feedback` (at most 100 items), `feedback_count`, `available_feedback_count`
and `feedback_truncated`. Feedback envelopes distinguish `available`, `erased`
and `unavailable`; only available entries include substantive `payload`.
Revoked or expired reviewer access does not erase Admin history. Current source
permission and retention still gate content. No source/report/transcript payload
or audio URL is returned. Unknown assignments return 404 and mismatched immutable
bindings return 409. This endpoint never calls the reviewer read API.

## Historical shared-session contract

This contract defines the server-managed review handoff from a completed Sales
Xray run to an assigned verified reviewer.  It defines transport shapes only;
the application loads every binding from the database and applies the existing
tenant, identity, recording, retention, and review ACLs before returning data.

The Academy form is `/sales-xray/review/[assignmentId]`.  A reviewer must be the
verified account identified by `reviewer_person_id` on the assignment.  The
ordinary reviewer routes do not require `admin_surface`, and a lens never
creates a role or grants access.

An email invitation is only a handoff into the normal account flow.  Its bearer
token is stored hashed (and encrypted only for the transactional email worker),
never grants source access by itself, and is accepted only by a normal verified
session whose email and active membership match the exact source tenant.

## Versioned DTOs

`ReviewAssignment` (`schema: ac.sales-xray.review-assignment/1`) is server
authored and contains:

| Field | Meaning |
| --- | --- |
| `id`, `tenant_id`, `run_id` | Stable assignment and exact tenant/run identity. |
| `run_generation`, `recipe_revision` | Run version used to detect stale assignments. |
| `source` | `tenant_id`, `recording_id`, `source_sha256`, positive `source_revision`, `permission_id`, and an opaque `provenance_ref`. No source payload is included. |
| `checkpoint` | Exact checkpoint `id`, tenant/recording/source binding, `stage`, `revision`, `cache_key`, `manifest_sha256`, and `payload_sha256`. |
| `reviewer_person_id` | The only account allowed to read and submit this assignment. |
| `allowed_lenses` | One or more of `sales`, `technical`, `ux`. |
| `state`, `created_at_epoch`, `expires_at_epoch` | Server lifecycle and expiry window. `assigned`, `in_progress`, and `submitted` are writable while unexpired; `revoked` and `expired` are terminal. |
| `created_by_person_id` | The authenticated server-side admin actor that created the assignment. |

`ReviewAssignmentCreateRequest` (`schema:
ac.sales-xray.review-assignment-create/1`) accepts only `run_id`,
`reviewer_person_id`, `allowed_lenses`, and `expires_at_epoch`.  Tenant, source,
checkpoint, creation time, and author are loaded or generated by the server.

`ReviewInvitationCreateRequest` (`schema:
ac.sales-xray.review-invitation-create/1`) accepts `run_id`, `invited_email`,
`allowed_lenses`, and `expires_at_epoch`.  The service verifies the same saved
report, permission, retention, and C2/C5/C6 lineage fences as direct assignment
creation, then writes an immutable invitation and one transactional outbox
event.  The raw token is never returned to the admin API or written to the
outbox payload.

`ReviewInvitationAcceptRequest` (`schema:
ac.sales-xray.review-invitation-accept/1`) accepts only `{ "token": "..." }` on
an authenticated reviewer session.  The UI may keep the token from the email
fragment while the person signs in or completes ordinary registration and
email verification, then posts it to the accept route.  Unknown, expired,
revoked, consumed, tenant-mismatched, and email-mismatched tokens return the
same `404`; acceptance creates the existing exact assignment once.

`ReviewFeedbackRequest` (`schema: ac.sales-xray.review-feedback/1`) is the
reviewer body:

```json
{
  "schema": "ac.sales-xray.review-feedback/1",
  "idempotency_key": "review-20260913-1",
  "lens": "sales",
  "evidence_refs": [{"checkpoint_id": "<server checkpoint UUID>", "span_id": "segment-12"}],
  "confidence": "high",
  "feedback": "The objection response is grounded in the cited segment.",
  "proposed_correction": {
    "target_layer": "context",
    "actual": "<observed value>",
    "expected": "<suggested value>",
    "rationale": "<why the suggestion is useful>"
  }
}
```

`proposed_correction` is optional and is stored as a suggestion separate from
feedback.  `ReviewFeedbackSubmission` adds server fields `id`, `assignment_id`,
`tenant_id`, `run_id`, `reviewer_person_id`, `author_person_id`, `lane`,
`request_sha256`, and `created_at_epoch`; its complete envelope is saved in `conversation_review_feedback`.
The server derives `author_person_id`
from the authenticated reviewer and derives `lane` from `lens`; neither is
accepted from the client.

The server resolves every `evidence_refs` pair against the exact assigned
checkpoint's existing run spans.  A missing, duplicate, or cross-checkpoint span
is rejected.  The request hash is the canonical hash of the request body and is
used with `(tenant_id, assignment_id, idempotency_key)` for retries.  Repeating
the key with the same hash returns the original immutable submission; repeating
it with different content returns `409` and does not append a second record.

## Routes

| Method and path | Caller and behavior |
| --- | --- |
| `GET /v1/conversation/review-assignments/{assignment_id}` | Assigned verified reviewer only. Returns the server-loaded assignment, report, transcript, evidence spans, and guarded audio source URL. |
| `GET /v1/conversation/review-assignments/{assignment_id}/source` | Assigned verified reviewer only. Streams the exact assignment source with server-checked byte ranges. |
| `POST /v1/conversation/review-assignments/{assignment_id}/submissions` | Assigned verified reviewer only. Validates the request, binds existing spans, and appends one submission. The body carries `idempotency_key`. |
| `GET /v1/conversation/review-assignments/{assignment_id}/submissions` | Assigned reviewer only. Returns that assignment's submissions authored by that reviewer; it never exposes another person's submissions. |
| `POST /v1/admin/conversation/review-assignments` | Requires the existing `admin_surface` and the configured AC operations control tenant. The request body contains no lineage or author; the server records the authenticated admin as `created_by_person_id`. An `Idempotency-Key` header is required. |
| `POST /v1/admin/conversation/review-invitations` | Same admin/operations check. Creates one exact-run invitation for the normalized email and emits the canonical email outbox event. An `Idempotency-Key` header is required; the response never contains the bearer token. |
| `POST /v1/admin/conversation/review-invitations/{invitation_id}/revoke` | Same admin/operations check. Appends an invitation revocation; a later token acceptance returns the generic invitation `404`. |
| `POST /v1/conversation/review-invitations/accept` | Requires the existing verified AC session and current source-tenant membership. The matching email account receives the existing assignment; the token alone never authorizes this route. |
| `GET /v1/admin/conversation/review-assignments` | Same admin and operations-control check. Accepts only a bounded `limit` of 1–50; no caller-supplied scope selectors. |
| `POST /v1/admin/conversation/review-assignments/{assignment_id}/revoke` | Same admin and operations-control check. Requires an `Idempotency-Key` header, appends the revoke decision, and prevents new submissions. Existing feedback remains append-only history. |

Assignment and submission lookup must return `404` for an unknown tenant-bound
identifier.  An assignment for a different authenticated person returns
`404`; an expired or revoked assignment returns `403`; an idempotency conflict
returns `409`.  These responses must not reveal source content or cross-tenant
existence.

## Lens and persistence semantics

| Lens | Existing `ConversationReview.lane` | Correction targets |
| --- | --- | --- |
| `sales` | `sales` | `context`, `profile`, `judge` |
| `technical` | `signal` | `transcript`, `measurement`, `attribution`, `alignment` |
| `ux` | `signal` | `ux_metadata` only; usability metadata, no canonical signal correction |

The lane mapping is fixed metadata and does not infer a reviewer role, score,
training label, or entitlement.  Every submission is append-only feedback; only canonical-layer corrections
also create a separate `ConversationReview` proposal on the existing sales or signal lane.  Feedback
and proposed corrections never apply canonical changes, update a profile,
publish an official score, or trigger training/retraining automatically.

The persistence adapter keeps the normalized `ReviewFeedbackSubmission` envelope
(including confidence, lens, idempotency, and evidence metadata) alongside the
existing review stream.  When a submission contains a canonical-layer
`proposed_correction`, the adapter passes that bounded correction through the
existing `review.validate_review_proposal` validator and stores its resulting
`ReviewProposal` separately.  A feedback-only submission has no invented target
layer and therefore does not enter that validator.  `ux_metadata` remains
review metadata and is never promoted to a canonical proposal.
